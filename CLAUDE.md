# FontanNet — Project Instructions for Claude Code

**Official title:** FontanNet: Growth-Aware, Decision-Focused Active Learning for Robust Pediatric Cardiovascular Conduit Design

**Team:** Aditya Shah, Rayansh Amitkumar Pande, Suraj Nautum Ganatra (Grade 10, Fort Bend ISD).
SEFH category: Biomedical Engineering.

## 1. What this project is

FontanNet is a high school research project (Regeneron ISEF 2027) testing whether a
**decision-focused active-learning algorithm** can find Fontan conduit designs that keep
blood-flow energy loss low across **multiple childhood growth scenarios**, using
**fewer CFD simulations** than standard methods (random sampling, standard Bayesian
optimization, a patient-specific Gaussian-process approach, and a reduced-order physics
model alone).

Background: in the Fontan procedure, a synthetic conduit routes blood from the inferior
vena cava to the pulmonary arteries. The conduit does not grow, but the child's native
vessels and blood flow do. A conduit that is efficient at implantation may perform poorly
later. We optimize designs to perform well across a set of literature-calibrated growth
scenarios rather than one predicted future anatomy.

**Central research question:** Can a physics-guided, decision-aware active-learning method
identify Fontan conduit designs that keep indexed power loss low across growth scenarios,
while requiring substantially fewer CFD simulations than conventional optimization under
an equal simulation budget?

This is an experimental computational research framework, NOT a clinical tool.

## 6. Physics and outputs

Starting assumptions (all in `configs/physics.yaml`, marked as assumptions the students
must justify in their paper):

- Steady, incompressible, laminar, Newtonian blood (density and viscosity values in config,
  `TODO(student): verify source`)
- Inlets: IVC (via conduit) and SVC with prescribed flow rates per growth stage and
  physiological condition (rest, and exercise if time allows)
- Outlets: left and right pulmonary arteries; outlet condition in config

Each finished case writes `results/summaries/<case_id>.json` containing:

- `case_id`, all input parameters, OpenFOAM version, machine name, wall-clock time
- **Power loss**: control-volume energy balance, sum over inlets minus outlets of
  (static pressure + dynamic pressure) × flow rate
- **Indexed power loss (iPL)**: power loss nondimensionalized by flow and body surface area.
  Implement the formula from the source paper the students provide.
  `TODO(student): provide source and exact formula`
- **Hepatic flow distribution (HFD)**: fraction of IVC (hepatic) flow reaching the left vs.
  right pulmonary artery, computed with a passive scalar released at the IVC inlet
- **Low-WSS area fraction**: fraction of conduit wall area below the threshold in
  `constraints.yaml` (`TODO(student): threshold + source`)
- Convergence info: final residuals, whether convergence criteria were met, iterations

Any case that fails to converge is marked `converged: false` and excluded from analysis
(not silently dropped — keep a count).

## 7. Design space and growth scenarios

- Design parameters (start with 2, max 3): conduit diameter, IVC-to-PA attachment offset,
  optionally attachment angle. Levels defined in `design_space.yaml`.
- Growth: the conduit keeps its implanted diameter; native vessels (SVC, PAs) and flow
  rates scale per growth stage. Start with **idealized parametric geometry**, where growth
  means changing vessel diameters and flows. Patient-specific anatomies come later and only
  after the idealized pipeline is validated.
- Reject geometries violating constraints in `constraints.yaml` before meshing.
- Robust objective: aggregate iPL across growth scenarios (default: mean; also support
  worst-case and a risk measure such as CVaR, selectable in config).

## 8. Methods to compare (all under the same CFD budget)

1. Random selection
2. Standard Bayesian optimization (GP + expected improvement) on the robust objective
3. Patient-specific GP optimization baseline (`TODO(student): which published approach`)
4. Reduced-order model alone (no ML correction)
5. **Ours: decision-focused acquisition** — chooses the next (design, growth stage,
   condition) simulation by its expected value for identifying the best robust design
   (knowledge-gradient style over design × environmental variables), using the
   reduced-order model as a physics prior with a learned correction.

The students must position method 5 against related literature (knowledge gradient,
Bayesian optimization of risk measures, optimization of expensive integrands). Keep the
implementation modular so a stronger published baseline can be added.

## 9. Benchmarking: lookup-based evaluation

- First, run the full **reference grid** with CFD.
- All methods choose only from grid points. Each "simulation" during benchmarking is a
  lookup in the reference results, so experiments run in seconds.
- Run every method with ≥20 random seeds per budget level.
- Metrics: simulations used, design regret vs. the grid's true robust optimum, verified
  iPL of the chosen design, performance on held-out growth scenarios, constraint
  satisfaction (HFD, low-WSS).
- Report means with confidence intervals. Report negative results honestly.
- Separate training anatomies from test anatomies (no data leakage).

## 10. Job system (two machines)

- `scripts/make_manifest.py`: builds `cases/manifest.csv` from configs (unique IDs,
  deterministic order, priority column: core grid first, then extensions).
- `scripts/assign_cases.py --shares pc=0.5,mbp=0.5`: interleaved assignment by measured
  speed (shares from the benchmark). Each case gets exactly ONE machine.
- `scripts/rebalance.py --shares ...`: reassigns only UNFINISHED cases.
- `scripts/run_worker.py --machine pc|mbp --parallel N --cores-per-case K`: runs only its
  own cases, **skips cases that already have a summary file** (safe restart), applies the
  storage policy (Section 15) after every case, logs to `logs/`.
- `scripts/benchmark_machine.py`: cases/hour for different parallel x cores settings.
- `scripts/cross_machine_check.py`: identical cases on pc and mbp must agree within 1%.
- `scripts/grid_status.py`: done / running / failed / remaining per machine, ETA, and
  current size of FONTANNET_DATA_DIR.

## 11. Development phases (do them in order)

Each phase has acceptance criteria. Do not start the next phase until the students confirm
the current one passes.

**Phase 0 — Scaffolding.** Repo structure, environment file, configs with placeholders,
`.gitignore`, pytest setup, `AI_USAGE.md`.
✅ Environment installs on both machines; `pytest` passes.

**Phase 1 — Fake objective.** A cheap analytic test function standing in for CFD, with the
same interface as the real pipeline. Implement all five methods and the benchmark harness
against it.
✅ Full benchmark runs end to end in minutes; plots generated.

**Phase 2 — Pipe validation + single CFD case.** Straight-pipe test against
Hagen–Poiseuille, then parametric idealized TCPC geometry, mesh, OpenFOAM case setup,
run, post-processing into a summary JSON.
✅ One case converges; power loss, iPL, HFD, low-WSS computed; students review flow fields.

**Phase 3 — Validation.** Mesh-convergence study (≥3 mesh levels); compare iPL to published
ranges for idealized TCPCs (students supply values); cross-machine check.
✅ Mesh-independent result chosen; values in a plausible range; machines agree within 1%.

**Phase 4 — Reference grid.** Manifest, machine benchmark, assignment, run all cases on both
machines.
✅ All cases complete or are logged as failed; summaries committed.

**Phase 5 — Reduced-order model + ML correction.** ROM for energy loss; correction model
trained on training anatomies only.
✅ Held-out prediction error reported for ROM alone vs. ROM + correction.

**Phase 6 — Real benchmark.** Swap the fake objective for reference-grid lookups; run all
methods with ≥20 seeds.
✅ Regret-vs-budget curves with confidence intervals for every method.

**Phase 7 — Patient-specific anatomies (if time allows).** Apply the pipeline to 1–2 public
anatomies.

**Phase 8 — Phantom support (if time allows).** Export selected geometries as STL for 3D
printing; script to compare flow-loop measurements with CFD predictions.

## 15. Storage policy (keep the project under 100 GB)

- Simulations run in `FONTANNET_DATA_DIR` on a local SSD folder, NEVER inside iCloud,
  Google Drive, OneDrive, or Dropbox. On `pc` it lives inside the WSL filesystem.
- After every case the worker: writes the summary JSON; deletes intermediate time
  folders and `processor*` folders; keeps full final fields ONLY for cases flagged
  `keep: true` in the manifest (validation cases and cases used in figures).
- OpenFOAM writes binary, compressed output and only the final converged time step
  (settings in `configs/storage.yaml`).
- Hard cap: if FONTANNET_DATA_DIR exceeds `cap_gb` (default 60), the worker pauses and
  prints a warning until space is freed.
- Archive: kept cases are compressed (`tar.gz`) and uploaded to the shared cloud folder
  every few days; delete the local copy only after the upload is verified.
